# 政工案例评分简化更新方案

日期：2026-10-26。状态：SCP04 逐项累计预览已实现并完成本地自动化验收；大屏模板及其余联调、部署待实施。

本方案沿用现有活动和多维度加权评分，更新两项能力：**单独增加可选的大屏模板**，以及**每填一项就累加显示**。主办方自行在评分细则中配置本次四个维度，评委继续使用现有手机评分、确认提交和回执流程。

本文件是[原完整方案](political-case-review-update-plan.md)的简化实施选项。原方案保留供后续扩展参考；本方案的实施范围与 checkpoint 独立记录。

## 一 直接使用现有评分配置

在活动的评分规则中选择“多维度”，按下表填写。步长可先建议为 0.1，最终以主办方确定的评分要求为准。

| 维度名称 | 满分 | 权重 |
| --- | ---: | ---: |
| “切口”聚焦度 | 30 | 30% |
| “成效”示范性 | 30 | 30% |
| “推广”难易度 | 20 | 20% |
| “复制”可能性 | 20 | 20% |

现有个人总分公式为 `100 × Σ（单项得分 ÷ 单项满分 × 单项权重）`。上述配置使个人总分等于四项原始分直接相加，满分为 100，27、28、18、19 分合计为 92 分。

各评委总分如何汇总，继续使用已有平均分或去最高最低分后平均。最低有效份数、评分时长、改分政策等使用已有设置，在发布前核对。仅选择大屏模板不会自动修改这些规则，也不会自动设置四个评分维度。

## 二 单独增加可选的大屏模板

在活动基本设置及主持人“大屏管理”中增加“展示模板”选项，提供“通用模板”和“政工案例模板”。所有活动均可选择，旧活动默认保持通用模板。布局模板与现有浅色、深色主题分开保存，两套模板均支持现有明暗选项；政工模板建议以深蓝、白字及少量金色作为深色视觉方向。

模板只决定布局、字号层级和展示文案。更换模板不改变活动类型、评分规则、评分结果或任务状态。已发布活动通过现有大屏设置接口切换，沿用版本冲突校验和实时同步机制。

### 大屏页面内容

首期复用现有六种展示模式，专用模板在这些状态下提供完整布局。

| 展示模式 | 政工案例模板内容 |
| --- | --- |
| 等待 waiting | 活动标题、主办单位、活动简介和可选加入二维码 |
| 评分中 progress | 案例编号、案例名称、简介、已交/应交人数、评分倒计时 |
| 暂停 paused | 案例信息、暂停提示、冻结的剩余评分时间 |
| 成绩 result | 大字号最终分、案例名称、有效评分份数、汇总方式和公布时间 |
| 排行榜 leaderboard | 名次、案例编号、案例名称、最终分；长榜单分页 |
| 结束 ended | 活动结束提示及已公布成绩总览 |

建议顶部放活动标题，中部突出当前案例和进度或成绩，侧边按设置展示二维码，底部保留同步状态。以 1920×1080 为主要设计尺寸，检查 1366×768 和 4K，兼顾长活动标题、长案例名称和大量案例分页。

首期直接使用现有对象的编号、名称和简介。申报单位、汇报人如需展示，可以由主办方写入案例简介，按原文展示，不从自由文本中推断或拆解结构化字段。活动 organization 仍表示主办单位。

大屏只展示已公布的最终成绩，不接收评委输入过程中的个人小计。该模板不硬编码四维规则或四维成绩条，确保选择模板与实际评分规则无关；若后续需要这些内容，再增加对应公开快照字段。

### 最小技术改造

- Event 增加 `screen_layout`，枚举建议为 `standard`、`case_review`，数据库默认值及旧活动回填为 `standard`。
- EventCreate、EventPatch、EventInfo 以及 ScreenSettings、ScreenDisplay 增加对应字段；公开展示对象通过 `display.layout` 返回当前布局。旧请求省略新字段时，创建沿用通用默认值，更新保留已有布局，避免被旧客户端意外重置。
- 创建、草稿设置和活动复制保留布局选择；发布后的切换仅走现有大屏设置接口。布局属于可修改的展示配置，无需新增评分模板版本或改变规则发布快照结构。
- 保留现有大屏入口、授权和订阅，把通用布局抽为 StandardScreen，增加 CaseReviewScreen，由统一页面按布局字段分发；CSS 独立作用域，避免影响旧模板。
- 大屏设置修改继续推进版本、刷新快照缓存并发送通知；模板切换后仍保持当前展示模式和对象。
- 更新 OpenAPI 及前端类型，覆盖旧活动兼容、活动复制、切换模板、断线恢复和授权失效。

重点文件为后端 events/models.py、events/schemas.py、events/publication.py、snapshots/schemas.py、snapshots/service.py 及新增迁移；前端 EventBasicFields.tsx、ScreenManager.tsx、ScreenPage.tsx、ScreenContent.tsx 和新增模板组件及样式。最终拆分以实施时的代码结构为准。

## 三 每填一项就累加显示

改造前，评委页在全部维度合法填写后显示“个人总分预览”，任一项未填或不合法时显示“待填写”。现已改为边填边显示有效项的累计分数，并明确当前填写进度。

| 输入状态 | 合计区域显示 | 是否允许确认提交 |
| --- | --- | --- |
| 全部空白 | 已填项合计 0.00；已填 0/4 项 | 否 |
| 第一项填 27 | 已填项合计 27.00；已填 1/4 项 | 否 |
| 第二项填 28 | 已填项合计 55.00；已填 2/4 项 | 否 |
| 第三项填 18 | 已填项合计 73.00；已填 3/4 项 | 否 |
| 第四项填 19 | 个人总分预览 92.00；已填 4/4 项 | 是，仍须满足开评、同步、截止等条件 |
| 第一项从 27 改为 29 | 个人总分预览 94.00；已填 4/4 项 | 是，仍须满足既有提交条件 |
| 删除第四项（第一项保持 29） | 已填项合计 75.00；已填 3/4 项 | 否 |

上述数字是本次四维配置的示例，组件应支持任意现有维度数量，不固定为四项。

### 计算与输入规则

1. 使用原有权重累加有效项贡献：`已填项合计 = 100 × Σ（有效项得分 ÷ 该项满分 × 原权重）`。不按已填项重新归一化权重，也不直接相加所有活动的原始分。例如“满分 100、权重 30%”的一项填 80，贡献应为 24 分。
2. 空白项不参与预览计算，仍保存为空白；合法零分参与已填计数。不会向输入框、草稿或提交数据自动写入零来替代缺填。
3. 非法数字、越界、非法步长等值不计入合计及合法填写数量，同时在对应输入项显示错误。此时合计标题改为“有效项合计”，附“有效 2/4 项，1 项需修正”等提示，不保留该项之前的合法分数贡献。
4. 所有项合法且填写完整后，标题切回“个人总分预览”；确认提交继续检查全部维度以及任务状态、截止时间、同步状态等现有限制。部分合计不作为可提交总分。
5. 继续使用 Big.js 十进制计算，先精确累计贡献，最后统一按两位小数 ROUND_HALF_UP 展示，避免逐项四舍五入后再相加。全部填完时必须与现有 personalTotal 和服务端结果一致。
6. 合计区保持在现有提交区域，支持输入、加减按钮、删除、草稿恢复和修改已保存评分后的即时重算。说明文案保留“仅供预览，保存结果以服务端回执为准”。

### 最小技术改造

建议在 `frontend/src/lib/decimal.ts` 新增独立的部分预览函数，返回合计、有效项数、总项数、错误项及是否完整。保留 `personalTotal` 原有严格校验语义；需要共用的计算逻辑可抽取，避免放宽原函数后让其他调用方把缺填视为有效评分。

`frontend/src/judge/ScoreCard.tsx` 接入新的预览结果，更新文案与填写进度，并明确在未填完或有错误时禁止进入提交确认。确认弹窗、保存接口及回执继续使用完整评分数据。此次累加功能只影响评委本人的输入预览，无需改变后端计分逻辑、评分单结构或大屏接口。

## 四 实施边界与排名待定事项

本方案不新增活动类型、固定规则模板接口、申报单位专用字段、案例介绍模式、收评待公布模式或四维公开成绩摘要。这些能力保留在原完整方案中，后续有明确需求再独立扩展。

统一排名与分类排名仍保留为待定选项，本次两项改造不替主办方作出选择。现有单活动榜单可用于统一排名；若确定分别排名，可以分别创建两个活动，各自配置相同评分规则并选择政工案例大屏模板。如果要求在同一活动内分榜，需另行实施分类字段和服务端分类排名，不能仅通过大屏过滤实现。最终组织方式应在录入名单和发布活动前确定。
