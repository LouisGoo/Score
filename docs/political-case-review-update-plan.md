# 政工案例评审活动类型更新方案

日期：2026-10-26。本文为项目更新方案，尚未实施业务代码、数据库迁移或部署。

建议新增“政工案例评审”活动类型，内置附件规定的四维百分制评分，配置独立的案例评审大屏，并复用现有评委身份确认、评分回执、收评、成绩公布、实时同步和导出流程。

## 一 业务依据与范围

依据用户提供的《1023附件2：全市公安机关政工行动计划“三可”实践案例暨特色政治工作评审指导意见和评分表  (1).docx》。附件正文标题为“评审指导意见和评分表”，包含以下四项评价维度及评价重点。

| 评价维度 | 满分 | 评价重点摘要 |
| --- | ---: | --- |
| “切口”聚焦度 | 30 | 紧扣公安部、省厅、市局任务清单；小切口、深挖掘；符合政工实际；背景和具体问题清晰 |
| “成效”示范性 | 30 | 机制、流程或方法有突破；举措有落地路径；有真实数据及前后对比；具有领先成效或解决长期痛点 |
| “推广”难易度 | 20 | 贴合日常工作习惯；机制、流程、方法尽可能适配地市、县市区、派出所三个层面 |
| “复制”可能性 | 20 | 本市领先，具备复制推广条件；有借鉴路径，可供其他单位参考 |
| 总分 | 100 | 四项相加 |

评委端应保留附件评价重点的完整文字，以上摘要用于本方案说明及大屏简版。附件没有给每条评价重点分配子分值，不应自行拆成新的评分项，也不应将“推广难易度”实现为反向计分。

附件未规定汇总算法、评分步长、最低有效份数、限时、同分处理、两个参评类别是否分别排名，以及大屏视觉风格。下文对此的设计均为产品建议，须在活动规则确定后固化。

首期按同一评委名单、逐案例开评的现有流程设计。若不同类别使用不同评委或需要同时评审，应另行增加评委分组和任务分配能力，不能只增加类别字段。

## 二 现有能力与缺口

| 模块 | 已有能力 | 本次需要补充 |
| --- | --- | --- |
| 活动 | 草稿、发布检查、发布快照、复制、结束和归档 | 活动类型及类型模板版本 |
| 规则 | 多维度、满分、权重、步长、平均分、去最高最低分后平均 | 四维预设和完整评价要点 |
| 参评对象 | 编号、名称、简介、出场顺序 | 申报单位、汇报人，可选参评类别 |
| 手机评分 | 多维评分、总分预览、确认提交、改分、回执 | 案例语义、评价重点、直接分值提示 |
| 大屏 | 六种展示模式、浅深主题、二维码、分页榜单、同步状态 | 独立页面布局、案例介绍、收评待公布、单位展示和四维成绩摘要 |
| 导出 | 汇总、逐维评分明细、审计 CSV | 案例字段与更便于现场核对的四维汇总列 |

当前 Event 没有 event_type，screen_theme 只有 light/dark；ScreenPage 和 ScreenContent 使用同一套布局。应将业务类型、布局模板、明暗配色与展示模式分开，避免将新类型塞进 screen_theme。

## 三 活动类型与评分规则

建议类型标识：generic（通用评分，兼容全部旧活动）和 political_case_review（政工案例评审）。创建页以类型卡片选择，活动列表显示类型标签；新类型默认应用本次评分模板。

| 内部维度标识 | 满分 maximum | 权重 weight |
| --- | ---: | ---: |
| focus | 30 | 0.30 |
| effectiveness | 30 | 0.30 |
| promotion | 20 | 0.20 |
| replication | 20 | 0.20 |

现有引擎的个人总分是 `100 × Σ(原始分 / 维度满分 × 权重)`。按上表配置，恰好等于四个原始分相加，无需增加新的计算算法。例如 27、28、18、19 分得到 92 分，四项满分得到 100 分。满分和权重不能按另一套公式重复相乘。

该类型首期固定四项名称、顺序、满分和权重，服务端同样校验，防止只在前端锁定。评价重点保存到规则 JSON 的 guidance 字段，并随发布快照冻结；旧规则缺少 guidance 时按空文本兼容。模板使用独立 template_version，不代替现有 rule_version。

建议初始设置为平均分、步长 0.1、最终成绩保留两位小数，发布前显式确认汇总算法和最低有效份数。正式评审建议全部评委交齐，即 K=N；这与现有默认约 80% 的最低份数不同，应在发布检查中按当前评委人数解析并展示。去极值可使用既有算法，但需要至少 5 位有效评委，并明确是按个人总分去掉一个最高分和一个最低分。

现有同分规则为并列排名（1、2、2、4），建议沿用；不自行添加“聚焦度优先”或自动奖项。评分时限与改分政策在发布前设置，附件未规定默认时长。发布后锁定类型、规则和案例资料，复制后形成可修改草稿。

## 四 操作流程与评委页面

主办方创建活动 → 选择政工案例评审 → 录入案例与评委 → 核对四项标准及汇总规则 → 发布 → 展示案例 → 开评 → 收评核对 → 公布 → 下一个案例 → 成绩总览与导出。

案例资料建议包含案例编号、案例名称、申报单位、汇报人（可选）、案例简介和出场顺序。活动 organization 仍表示主办单位，不能复用为各案例申报单位。名称沿用现有 80 字上限，足以支持多数案例题目；大屏通过分行和布局适配长标题。

评委页面顶部展示案例名称和申报单位，主体为四张评分卡。每张卡显示维度、满分、简要提示和可展开的完整评价重点；底部显示“合计 / 100 分”。该类型不展示容易误解的通用权重提示。未填与零分继续区分，四项均合法才允许核对提交。

继续使用现有确认、回执、幂等提交和改分机制，不新增第二套评分接口。主持人控制台将“对象”替换为“案例”，增加“展示案例”和“收评待公布”的操作及预览。

## 五 专用大屏设计

建议采用深蓝背景、白色主文字、少量金色强调的正式会场风格，以清晰呈现案例、单位和分数为主要目标。视觉方向为建议，可按主办方会场主视觉调整。独立模板应改变信息布局、字号层级和各状态内容，而非只替换背景颜色。

以 1920×1080 的 16:9 大屏为设计基准，同时覆盖 1366×768 和 4K。固定顶部标题区、中央主体区和底部状态区；预留约 4% 边缘安全区。案例长标题允许两行，长榜单分页，不以压小所有文字来容纳内容。二维码在候场时醒目，正式评分及结果页按主办方设置缩小或隐藏。

| 展示状态 | 主要内容 | 对应模式和约束 |
| --- | --- | --- |
| 会场候场 | 活动全称、主办单位、四项评分标准、加入二维码 | 复用 waiting |
| 案例介绍 | 案例编号、名称、申报单位、汇报人、简介 | 新增 presentation；选择 PENDING 案例，只切换展示，不开放评分 |
| 正在评分 | 中央案例信息；右侧已交/应交与评分倒计时；底部四维标准 | 复用 progress，要求 OPEN；仅展示进度，不展示实时得分 |
| 暂停评分 | 保留案例信息，明确暂停及冻结剩余时间 | 复用 paused，要求 PAUSED |
| 收评待公布 | 当前案例、已收评、等待核对公布 | 新增 reviewing，要求 CLOSED；不得输出未公布成绩 |
| 成绩公布 | 突出最终总分，附四维汇总条、申报单位、算法和有效份数 | 复用 result，要求 PUBLISHED |
| 成绩总览 | 名次、案例名称、申报单位、最终分，分页展示 | 复用 leaderboard；只含已公布成绩 |
| 活动结束 | 活动结束说明和最终成绩总览 | 复用 ended；要求已结束或归档 |

成绩页布局建议：顶部为活动标题；中部左侧约 60% 放案例名称、单位和最终总分，右侧约 40% 放四个横向分值条；底部展示有效份数、汇总方式和同步状态。评分页保留类似结构，将成绩区换成提交进度和剩余时间。分值条同时标明原始分及满分，长度按各维度自身满分归一化。

四维汇总必须由服务端依据冻结的收评结果生成。平均分模式使用全部有效评分；去极值模式沿用总分计算已经选定的有效评委集合，不能对每个维度独立去极值。公布前不向大屏接口返回四维得分、个人评分或评委身份。每项汇总独立显示两位小数时，相加可能与最终总分有 0.01～0.02 分舍入差；总分以权威最终成绩为准，不在浏览器重新求和覆盖。

案例介绍不启动计时。首期只保留评分倒计时；若现场还需汇报倒计时，应作为独立计时功能设计，不能把介绍展示与开评绑定。

## 六 数据与技术改造

建议新增业务字段，使用明确模型和枚举，不将所有数据堆进任意 JSON。

| 位置 | 建议字段或变化 | 兼容与约束 |
| --- | --- | --- |
| Event | event_type、template_version、screen_layout | 旧活动回填 generic 与 standard；新类型默认 case_review；布局标识与业务类型分离 |
| Entry | submitting_unit、presenter；category 按分类需求决定 | 旧对象使用空值兼容；新类型发布时校验申报单位必填；类别不从名称推断 |
| CriterionInput | guidance | 可选、限制长度；随规则发布冻结；旧 JSON 可正常读取 |
| EventSnapshot | event_type、template_version，以及扩展后的 entries 和规则内容 | 保存本次活动实际使用的模板及案例资料；旧快照按兼容默认值读取 |
| ScreenSettings / ScreenDisplay | layout；增加 presentation、reviewing 模式 | 前后端联合校验类型、布局、模式及目标任务状态，保留现有版本冲突检查 |
| PublicRound / PublishedResult / RankingInfo | 申报单位等经过筛选的公开案例信息 | 主办方、评委、大屏及导出语义一致 |
| ScreenSnapshot | 四维标准摘要、已公布结果的 criterion_summary | 后端按发布与收评快照构造，不暴露原始 ballots 或完整管理快照 |

模板预设以服务端为权威，建议提供只读活动模板接口，让创建页获取名称、规则和默认布局，避免前后端各硬编码一份标准。草稿创建与更新、发布检查和复制流程都必须处理新字段。修改类型只允许草稿，并显式提示会重置哪些规则；发布后不能更换。

大屏前端继续使用同一个入口和数据订阅。将现有布局抽为 StandardScreen，新建 CaseReviewScreen，通过 display.layout 分发；全屏、授权失效、断线提示和重连机制共用。新模板 CSS 使用独立作用域，避免改变旧活动外观。未知布局应提示需更新页面，不默默展示错误模板。

展示模式只增加到大屏状态中，不增加 ScoringRound 业务状态。同步更新自动切屏逻辑：新类型开评进入 progress，暂停进入 paused，收评进入 reviewing，公布进入 result，结束进入 ended；补评重新进入 progress。保持通用活动原有自动切屏行为。

修改展示设置、发布成绩等操作须沿用 screen_version、快照缓存失效和 outbox 通知链路，包含 worker 到期收评路径。新增字段若只写数据库而未进入快照或未提升版本，大屏将无法可靠更新。

后端重点涉及 events、snapshots、results、exports 和 core/streams.py 中的自动切屏逻辑；评分引擎 scoring.py 复用。前端重点涉及 EventCreatePage、RulePanel、EntriesPanel、ScoreCard、ScreenManager、ScreenPage 和 ScreenContent。接口完成后重新生成 openapi.json / schema.d.ts，并更新手册与 API 文档。

现有排名在 results/service.py 与 snapshots/service.py 均有构造逻辑。如增加分类排名，应提取共用排名组装函数，避免控制台、大屏、接口和导出结果不一致。

## 七 分类与导出

“三可实践案例”和“特色政治工作”是否分别排名，不能仅依据文件名确定。在主办方明确前，本方案保留两种实现路径，不将某一种描述为附件要求。

| 选择 | 数据与大屏行为 | 实施影响 |
| --- | --- | --- |
| 统一排名 | 可保留类别作为标签；全部案例进入同一个榜单 | 最小改造路径 |
| 分类排名 | 案例必须有 category；活动保存 ranking_scope=category；服务端按类别独立计算名次；大屏分榜显示 | 需同时修改发布校验、排名接口、各角色快照、导出和测试 |

分类排名不应仅在大屏对总榜做筛选，否则名次会出现跨类别跳号。排名范围和案例分类均在发布时冻结。若不同类别实际评分标准不同，需扩展为分组规则或拆成两个活动，本次附件不足以支持推定两套标准。

继续提供现有 CSV 汇总、明细和审计下载，新增活动类型、申报单位及选用的类别字段。增加面向本活动的汇总视图或 CSV 列：四项汇总分、总分、名次、有效份数及汇总算法；数值和大屏使用同一来源。逐评委四维记录继续保留。Excel 专用排版和按附件生成签字评分表可作为后续扩展，不列为首期必要条件。

## 八 分阶段交付与验收

| 阶段 | 交付内容 | 完成条件 |
| --- | --- | --- |
| 1 规则与视觉定稿 | 汇总算法、份数要求、分类口径；候场、评分、公布、总览四种主要画面原型 | 确认信息层级、长标题、单位展示与现场分辨率 |
| 2 类型与资料 | 数据迁移、类型模板接口、创建设置、案例字段、发布冻结与复制 | 新旧活动可创建发布；旧快照正常读取；复制保留新资料并清除评分和凭证 |
| 3 评分与大屏 | 四维评分提示、专用模板、介绍及待公布模式、四维公开摘要、同步链路 | 一次完整开评至公布流程通过，界面与服务端结果一致 |
| 4 结果与现场验证 | 排名及导出、回归、手机和大屏实机演练、上线文档 | 新旧活动均完成验收，目标环境迁移和部署验证后可使用 |

关键验收用例：

1. 四项满分得到 100；27+28+18+19 得到 92；缺填不能提交、零分可提交、越界及非法步长被拒绝；前后端结果一致。
2. 平均与去极值遵守既有算法；不足 K 不可公布；改分不增加已交人数；四维摘要与总分使用同一有效评委集合。
3. 介绍页不开放评分、不消耗评分时长；手动收评与 worker 到期收评均正确进入待公布；补评、暂停、恢复、公布和结束均正确切屏。
4. 公布前，大屏响应中没有总分、四维得分和原始评分；公布后与控制台、导出相符；大屏授权撤销后清空画面。
5. 断线重连、刷新和旧版本冲突后取得最新快照；新模板不会影响通用活动大屏。
6. 长活动名、长案例名、中文单位名、大量案例分页在 1366×768、1920×1080 和 4K 下可读；微信手机评分与现场屏幕完成实际演练。
7. 如选分类排名，覆盖分类间相同分数、类别内并列、空类别榜单，以及管理端和大屏名次一致。
8. 升级前备份并在测试库演练；旧活动及历史结果不重新计分，旧发布快照缺少新字段仍可查询、复制和导出。

验证使用仓库现有前后端测试、真实 MySQL 集成测试、接口契约检查和构建。当前只是方案编写，没有运行或宣称这些新增功能测试通过。部署应先做增量数据库迁移，再发布支持新字段的后端与前端，最后启用新类型；回退时停止创建新类型并保留已有数据，不以删除新字段作为常规回退手段。

首期优先完成新增类型、四维模板、申报单位、专用大屏和可靠成绩导出。复杂材料上传、独立汇报计时、自动奖项、分组评委以及打印签字表按实际现场需求另排，避免扩大本次活动前的交付范围。

## 九 更新 Checkpoint 列表

以下清单用于逐批实施与验收，编号保持稳定，便于在提交和 review 记录中引用。当前仅完成方案编写，所有实施 checkpoint 均未完成。每项完成后勾选，并在对应 checkpoint 下补充提交号、验证日期、检查结果和证据链接；存在跳过项或未测项时明确记录，不以代码完成代替验收完成。

排名方式目前暂未确定，按用户要求保留统一排名和分类排名两种方案。选择记录与实现进度分别维护，不把尚未决定的分类需求默认标为已确认。

- [ ] 核对四项名称、评价重点、30/30/20/20 满分和总分 100，明确不拆分子分值。
